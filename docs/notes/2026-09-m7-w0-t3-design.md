## (i) Where rung A runs today, and what a tier-solved rung replaces

`run_elastic_ladder` (`sqp_solver.cpp:1082`) takes a `QpEngine &` and solves each rung at `:1133` — `qs_e =
engine.solve(elastic.qp, seed_elastic, elastic_overrides)`. That is THE call. Two callers, both passing the driver's
walk `*engine_`: the certified fallback under `kIpm` (`:1278`, floor retry `:1289`, from `:3968`) and the walk route's
own `kInfeasible` consumer (`:5505`) — the second reachable in EVERY mode, restoration's sub-driver included.

A tier-solved rung replaces that one call with `IpqpEngine::solve(elastic.qp, seed, iopts, overrides)`
(`include/hven/detail/qp/ipqp_engine.h:564`). No engine-side elastic form is needed: the elastic problem is already a
plain `QpProblem` with `n + ns` variables and the same `me`/`mi` (`elastic.h:85–89`, built at
`src/globalization/sqp/soc_elastic_restoration.cpp:56`). Two things it may NOT reuse:

1. **`ipqp_result_to_qp_solution` (`sqp_solver.cpp:921`) FORCES `status = kOptimal`.** The ladder breaks on
   `qs_e.status != kOptimal` (`:1148`) and the usability/exhaustion verdict reads the same field (`:1199–1212`), so a
   forced `kOptimal` would turn every tier escape into "this rung solved" — a silent false certificate. The tier path
   derives the rung's status from `ipqp_exit_is_a_usable_step` (`:831`) and never synthesizes `kInfeasible` (spec
   §6.3: the barrier tier yields a signature, never a certificate).
2. **The trust-region override.** The walk rung passes a DEFAULT `SolveOverrides` on purpose (`:1130–1132`: "passing
   it here would cap the SLACKS at Delta too"), because the walk ignores it once the window is in the box. The tier
   does not: `ipqp_effective_tr_radius` (`src/qp/ipqp_engine.cpp:558`) resolves the `+inf` sentinel to
   `opts.qp.tr_radius` and `make_ipqp_box` (`:424`) windows all `n + ns` columns around `clamp(0, l, u)`. At the
   shipped default (`QpOptions::tr_radius = +inf`, `include/hven/qp/qp_types.h:165`) the window is disabled and
   nothing happens; with a finite `qp.tr_radius` the slacks are capped a SECOND time (the driver already folded that
   radius into the elastic box at `:5500`), and since the witness point's scaled slack is `min(|r_j|, 1) <= 1`
   (`slack_scale = max(1, |r_j|)`, `soc_elastic_restoration.cpp:84`) a window below 1 cuts off the
   feasible-by-construction witness. **Decision: the tier rung runs on an engine built from a `QpOptions` copy with
   `tr_radius = +inf`, asserted at the call.**

## (ii) A9 — how a second symbolic analysis is charged and read

The tier holds one analysis per instance, keyed on the pattern: `analyzed_` (`ipqp_engine.h:587`) is cleared when
`layout_.sync` relays (`src/qp/ipqp_engine.cpp:1634–1636`); `factorize_once` (`:1593`) then pays `kkt_.compute()`,
otherwise the FIRST factorization of each `solve()` pays one `refactorize(kVerify)` and the rest declare; the census
differences `analyze_count` (`:2858`). A9's driver half pins both `ipqp_symbolic_analyses == 1` per solve AND
`analyses + verifies == major_iters` (`tests/sqp/test_ipqp_dispatch.cpp:397–414`).

**A shared instance is the wrong answer.** The elastic pattern differs in dimension, so on `ipqp_engine()` a rung
relays the layout (+1 analysis) and the next major's primary solve relays it back (+1) — two per activation, and A9's
second clause breaks by construction. It also destroys the cross-major carry: `carry_` is overwritten at the elastic
dimension (`ipqp_engine.cpp:2741–2753`) and the driver's size check (`sqp_solver.cpp:3823–3827`) drops it cold.

**Recommendation: a SECOND, dedicated `IpqpEngine` for the elastic pattern**, lazily built as `ipqp_engine()` is
(`sqp_solver.cpp:6172`). The primary's hoist is then untouched and **A9 is PRESERVED, not re-stated** — its fixture
(HS26) never fires the rung, and elastic analyses are counted on their own instance's entries. Within one ladder the
pattern does not move (`set_elastic_penalty` writes `g` only, `elastic.h:191–193`), so the charge is **+1
`ipqp_symbolic_analyses` on a solve's first activation, then +1 `ipqp_pattern_verifies` per rung**, with a further
analysis only when `ns` or the linearization pattern moves between activations. A9's *sum* clause becomes a
per-instance statement, said so in a dated comment; its numbers do not move.

## (iii) The singular slack block and the certification read

`build_elastic_subproblem` copies only the original `H` into an `n2 x n2` matrix
(`soc_elastic_restoration.cpp:97–104`), so the `ns` slack rows/columns of `H` are structurally EMPTY. Three mechanisms
cover it, a smaller risk than the W2 plan assumed: the layout reserves a diagonal in every row
(`src/qp/ipqp_kkt_layout.cpp:185`, `:211–213`); the primal diagonal is written as `H_ii + rho_sched + sigma_i`
(`src/qp/ipqp_engine.cpp:1561–1575`) with IP-PMM's proximal `rho_sched >= ipqp_rho_init > 0`; and every slack carries
BOTH finite bounds (`[0, violation_l1 / sigma_j]`, `soc_elastic_restoration.cpp:146–157`), so the condensed bound
curvature `sigma_i` is strictly positive there too. The inertia target `expect_pos = n + ns + mi`
(`ipqp_engine.cpp:1239`) is therefore structurally attainable — the block is not singular in the assembled KKT. The
exposure is quantitative, and is READ in `ipqp_rho_demanded_max`/`_last` (`include/hven/core/solver_counters.h:506`,
`:516`), `ipqp_inertia_retries` (`:526`) and `ipqp_final_inertia_read` (`:626`). `ssn_certify_from_face`
(`sqp_solver_types.h:554`) is an SSN lever, not on this path.

**The failure mode that matters is the opposite one.** The elastic QP is FEASIBLE BY CONSTRUCTION, so a §6.3
infeasible-suspect escape on it is by definition a false positive — and it would fire in exactly the regime
(rank-deficient curvature wanting a large `rho_dem`) the detector was hardest to settle. The consequence is bounded:
the rung reads non-`kOptimal`, the ladder breaks, and the driver falls to the exhaustion certificate or rung B. That
is a ROBUSTNESS loss (a feasible relaxation declared exhausted), not a wrong certificate — the `kInfeasible` is still
synthesized by the driver from the slack `l1` (`:1208`, `:1314–1320`).

one thing — an interior-point solve of a large, feasible, degenerate-curvature QP where the active-set walk may not
terminate in time.**

## (v) The toggle

`SqpOptions::elastic_rung_engine` ∈ {`kWalk` (default), `kTier`}: a named enum field beside `qp_mode`
(`sqp_solver_types.h:515`), hand-validated in `validated()` (`src/drivers/sqp_options.cpp:272–278`) by refusing the
enumerator-count sentinel as `qp_mode` does, and dumped by `dump_options` (`sqp_options.cpp:452`). The dump moves
three T5 drift-pin constants — `kSqpOptionsFields` 25, `sizeof(SqpOptions) == 376`, `kSqpDumpLines` 56
(`tests/drivers/test_options_dump.cpp:72`, `:112`, `:133`) — a declared, mechanical re-pin. **Allowed in EVERY mode,
not gated on `qp_mode == kIpm`**, because rung A is reachable from the walk route too (`:5505`); gating would make one
field mean different things per mode.

**The pin `SqpDriverSsnMode.RestorationStaysOnTheWalkUnderKSsn` (`tests/sqp/test_sqp_solver.cpp:7685`) is about
RESTORATION, not about the elastic rung.** It pins `ropts.qp_mode = QpMode::kWalk` (`sqp_solver.cpp:4199`) through the
counters that line moves (131 SSN iterations, 234 factorizations); it says nothing about which engine solves a rung,
and is **UNCHANGED** here. Its *rule* applies by analogy: `ropts = opts_` (`:4158`) would carry `kTier` into a
sub-driver whose own walk route reaches `:5505`, so phase 2 adds `ropts.elastic_rung_engine = kWalk` beside `:4199`
with a dated comment. At the default that changes nothing and no pinned number moves.

## (vii) The one risk for the owner

**The measurement that would decide the default cannot be taken on the populations the rule allows.** F7 never fires
the rung; HS fires it but is TRAIN-embargoed until W1 H2; the constructed fixtures that fire are two-variable problems
where the tier can only lose. Shipping `kTier` OFF on that evidence is correct by the M7 exit criterion — a heuristic
that cannot show a win ships disabled — but the toggle would land unvalidated on any problem like the one the
robustness argument is about, and the decision would move to M7 W2's TRAIN re-read or to the suite. The alternative is
to build the large inconsistent cell first and measure on it: the honest version, at the cost of one fixture.

## (viii) Step 2a's amendment (2026-09-15): the vehicle, the measurement, the two registered hazards

The settler rescoped phase 2 on §(vi)'s finding: build the vehicle and price the WALK first,
and build the tier path only if the walk is shown to struggle. Both are now done and measured.

**The vehicle.** `tests/sqp/support/elastic_rung_vehicle.h` — `F7CollocationChain` plus ONE scaled
contradictory equality pair (`s (a^T x - b) = 0` and `s (a^T x + b) = 0` over the last node's

point, so the linearization is inconsistent at every iterate by construction. Pinned in
`tests/sqp/test_elastic_rung_vehicle.cpp` at N ∈ {100, 200, 400, 800} (Release; Debug sweeps the
two small sizes — declared in the file): `elastic_from_ipqp_escape >= 1` and the escape is the

**The measurement** (one major per size, so each size is one tier escape, one fallback entry, one
ladder; counters asserted, wall informational; three Release replicates byte-identical, Debug
identical on the two sizes it runs). Evidence retained at `.scratch/m7t3/STEP2A-EVIDENCE.md`:

| N | n | ladder rungs | rung minors | rung factorizations | tier's own factorizations | instructions |
|---|---|---|---|---|---|---|
| 100 | 500 | 6 | 312 | 184 | 10 | 4.08e9 |
| 200 | 1000 | 6 | 612 | 484 | 10 | 1.60e10 |
| 400 | 2000 | 6 | 1212 | 1084 | 10 | 6.57e10 |
| 800 | 4000 | 6 | 2409 | 2281 | 10 | 2.74e11 |

**The reading: the walk DOES struggle, and the 2b trigger is met on its third clause.** No rung
DNF'd, no budget was hit and no ceiling bound — so the first two clauses are NOT met — but the
rung's factorizations grow LINEARLY in `n` (184 → 2281, ratio to `n` rising 0.37 → 0.57) while the
primary tier solve's stay CONSTANT at 10 at every size. The rung-to-primary ratio is 18 : 1 at
N = 100 and 228 : 1 at N = 800, and diverging; instructions grow ~N² (4× per doubling). The
mechanism is visible in `rung_max_minors`: the ladder's six rungs cost ~`0.6 n` minors for the
FIRST one and ~2 each for the other five, so the hot chain is working exactly as designed and what
is expensive is the COLD FIRST RUNG — an active-set solve from cold on an `n + ns` problem, whose
iteration count an active-set method cannot make sublinear in the active set. An interior-point
rung has no such scaling. That is the owner's robustness case, measured.

**REGISTERED HAZARD 1 — the forced `kOptimal`.** `ipqp_result_to_qp_solution`
(`sqp_solver.cpp:921`) sets `qs.status = QpStatus::kOptimal` unconditionally. It is correct at its
two present call sites (`:3903`, `:6212`), which have already judged the exit usable, but any
future caller that maps a tier result for the ladder — whose loop breaks on `status != kOptimal`
(`:1148`) and whose exhaustion verdict reads the same field (`:1199–1212`) — would convert every
tier escape into "this rung solved". Latent today, load-bearing the moment a tier rung is built.

**REGISTERED HAZARD 2 — the tr-radius override windows `n + ns` columns.**
`ipqp_effective_tr_radius` (`src/qp/ipqp_engine.cpp:558`) resolves the `+inf` sentinel to
`opts.qp.tr_radius`, and `make_ipqp_box` (`:424`) then windows EVERY column. The walk rung is
immune by design (`sqp_solver.cpp:1130–1132`); a tier rung is not. Inert at the shipped default
(`QpOptions::tr_radius = +inf`, `qp_types.h:165`) and live for any caller with a finite
`qp.tr_radius`, where the slack columns — already bounded by the elastic construction — would be
windowed a second time around `clamp(0, l, u)`. Neither hazard is fixed here; both are recorded so
a later reader does not rediscover them from a wrong answer.

## (ix) Step 2b's disposition (2026-09-15): built, measured, and shipped OFF

The settler ruled GO on step 2a's clause-3 trigger. The toggle and the tier path are built as
§(i)–(v) specify. What landed, and what the measurement then said:

**Built.** `SqpOptions::elastic_rung_engine` ∈ {`kWalk` (default), `kTier`}, hand-validated against
the count sentinel on `qp_mode`'s discipline and dumped in declaration position (the T5 drift pin
moved: arity 25 → 26, `sizeof(SqpOptions)` 376 → 384, dump lines 56 → 57). The rung path goes to a
DEDICATED `IpqpEngine` (`SqpSolver::elastic_ipqp_engine`), its status comes from
`ipqp_exit_is_a_usable_step` mapping an unusable exit to `kMaxIter` and never to `kInfeasible`, and
its counters are charged to the engine-agnostic `SqpCounters::{qp_minor_iters, factorizations,
symbolic_analyses}` — `minor_iters` carrying `ipqp_iters`, so the probe budget still reads one unit
per subproblem-solver iteration. **Hazard 2 is FIXED here** because 2b needs it: the elastic engine
is built from a `QpOptions` copy with `tr_radius = +inf`, and the fix has its own pin, mutation-
proven (without it the same cell reads 11 rungs / 327 factorizations against 5 / 73).
`ropts.elastic_rung_engine = kWalk` sits beside the restoration `qp_mode` line; at the default both
are inert and no pinned number moves.

**A9 is preserved, not re-stated,** and that is what the dedicated instance buys: the elastic
pattern never reaches the primary tier's engine, so `analyses + verifies == major_iters` still holds
on BOTH toggle states (asserted per arm), and the elastic engine's own analyses land in
`SqpCounters::symbolic_analyses`, where every kernel's are counted.

**Measured** (`docs/notes/data/2026-09-m7-w0-t3-elastic-rung/`, three replicates byte-identical):
the tier rung's factorizations are **flat in n** — 73, 71, 73, 75 across N = 100…800 — against the
walk's linear 184, 484, 1084, 2281. At N = 800 that is 30× fewer factorizations, 63× fewer
instructions, 84× less wall. The design's central prediction is confirmed.

**And the finding that cuts the other way.** At every size, 3 of the tier's 5 rungs exit
non-optimal and one fallback entry falls through to rung B. Diagnosed: every one of those declines
is `kInfeasibleSuspect` — the §6.3 detector firing on an elastic QP that is FEASIBLE BY
CONSTRUCTION, i.e. precisely the false positive §(iii) predicted in advance, and not a budget
effect (raising `ipqp_max_iter` to 200 and 600 moves no counter). No wrong certificate is possible
— the tier cannot produce `kInfeasible` and the driver owns the verdict — but the rung is declined
more often than taken, and on the two-variable W2 T7 fixture the solve reaches `kInfeasible`
through rung B WITHOUT the certificate the walk arm produces.

**Disposition: `kWalk` stays the default and the toggle ships OFF**, on two independent grounds —
the M7 exit criterion (the win is on a constructed family, not the TRAIN split; W2 re-reads it) and
the false positives above (a 30× cost win is not worth an unmeasured reliability regression). The
two things that would move it are named in the artifact's §6. **Registered**: an escape census for
the elastic engine that does not collide with the primary tier's per-instance `solve` id — the
reason the decline REASON needed a throwaway diagnostic build rather than a boundary observation.
