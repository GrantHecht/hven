## 1. The problem, in one paragraph

The two engines were migrated from two projects and joined by warm-start currency. Today nothing on
their public surfaces is spelled the same: five phase-named IPM entries returning a bare vector against
one `solve` returning a value; fifty validated setters on a mutable settings object against ctor-frozen
options with no accessor; two status enums with the same integer shape and different names and
namespaces; two result structs, two counter models, two iterate-row types, a residual vocabulary that
collides; one warm-start payload with two protocols; a per-iteration callback on one side only; and —
underneath all of it — two model contracts, because `NonLinearProgram` owns the IPM's KKT workspace
(seventeen of the twenty model calls in the IPM loop are KKT assembly, pivots, slack diagonals and
reduced-space maps that exist nowhere else) while the SQP builds its own KKT from an evaluation seam over
any `ClaimStreamSource`. The inventory's "where the seams show" section lists the eight a consumer hits
first.

## 2. Group 1 — one model contract: the KKT workspace leaves the model

**Claim.** After group 1 both engines consume `ClaimStreamSource &` (the M4 claim-stream protocol), and
`NonLinearProgram` is a model, not a solver workspace.

- `NonLinearProgram` derives from `ClaimStreamSource`. It already implements the protocol's seven
  methods (`kkt_claim_rows/cols`, the three claim blocks, `objective_gradient_claim_rows`,
  `claim_stream_epoch`) with matching signatures; they gain `override`. From that commit the SQP's
  `AggregateEvalSeam` can take a partitioned program directly, which retires tycho's hand-written
  `SqpModelAdapter`.
- The IPM's KKT workspace becomes `IpmKktWorkspace` in `include/hven/kkt/` (+ `src/kkt/`), the
  component CLAUDE.md §2 reserves for "KKT assembly and layout". It owns what the model owned for the
  IPM: the KKT coefficient buffers and their fill/perturb operations (`fill_solver_coeffs`,
  `perturb_kkt_p_diags`, `perturb_kkt_c_diags`, `assign_kkt_slack_hessian`), the pivot and slack
  diagonals (`set_primal_diags`, `set_slack_diags`, `set_e_pivots`, `set_i_pivots`,
  `set_slacks_ones`), the sparsity analysis (`analyze_sparsity`), and the reduced-space maps
  (`gather_reduced_x`, `scatter_full_x`, `reduced_to_full`, `reduced_primal_vars`, `is_reduced`).
  It is built from the aggregate's declaration and claim tables and is refreshed on the structure
  epoch. `NonLinearProgram` keeps pieces, partitions, bounds, evaluation, identity and the claim stream.
- **Fixed-variable treatment is an IPM option**, not a model mutation (`configure_variable_treatment`
  leaves the model). The reduced space is a workspace property: the model no longer changes shape when
  the solver's treatment changes. Results are reported in DECLARED space on both engines; the IPM's
  bound duals are scattered back from the reduced space by the workspace.
- **Cross-solve reuse survives.** The IPM's symbolic analysis and pattern hash are keyed on the
  aggregate's structure epoch and declaration key — the same keying the SQP uses for hot warm-start
  reuse — so binding the model per call costs no re-analysis while the structure holds.
- **What group 1 does not change:** how the IPM evaluates. Model-side evaluation, partition parallelism
  and the claim stream are untouched; only who owns the KKT buffers changes.

**Proof.** A real code move: per-symbol identity is NOT the claim. The claim is trajectory identity —
the U0 27-cell three-arm replay 0/75, the interior and model suites, the HS pins, the golden rig's
old-seam arm — plus the T6 runtime protocol (ownership doc §11: pass A + pass B, the ±0.5 % corpus bar)
because the IPM hot loop re-lays. Install smoke + export contract.

## 3. Group 2 — the shared surface

One commit per concern, in this order; each holds the tree green and migrates tests and bench.

### 3.1 Classes and options
- `IpmSolver` (`include/hven/drivers/ipm_solver.h`) and `SqpSolver` (`drivers/sqp_solver.h`), both in
  `hven::solvers`, both movable and non-copyable (each owns backend sessions). `InteriorPointSolver` and
  `SqpDriver` go (the file renames land with group 3's sweep so group 2's P-SYM maps stay small; the
  class renames are group 3 too — group 2 changes SHAPE under the old names).
- `IpmOptions` and `SqpOptions`: aggregate structs, bare `snake_case` fields (CLAUDE.md §4 — the IPM's
  trailing underscores go). Each embeds one `CommonOptions common` for the concerns both have:
  `threads`, `reproducible_threads` (the IPM's CNR mode), `print_level`, `start_level`. Everything
  engine-specific stays engine-specific: the SQP's nested `QpOptions`/`IpqpOptions`; the IPM's barrier,
  acceptance, inertia, restoration, watchdog, return-best and sparse-backend knobs (the backend knobs
  are not promoted to common: the SQP's IPQP tier reaches the same `linear/` layer through
  `QpOptions`, and folding them is a later task if it is ever wanted).
- Validation: one free function per struct (`validate(const IpmOptions &)`, `validate(const
  SqpOptions &)`) throwing `std::invalid_argument`, run at construction and at replacement. The IPM's
  member `Settings::validate()` and the SQP's `validate_sqp_options` are these.
- Construction: `explicit IpmSolver(IpmOptions = {})`, `explicit SqpSolver(SqpOptions = {})`. `const
  XOptions &options() const` on both. `void set_options(XOptions)` on both, legal between solves only
  (a solve in flight is a `std::logic_error`). The IPM's ~50 validated `set_*` methods, its four static
  `strto_*` parsers and its six string-taking setter overloads GO — string parsing is the bindings'
  job. Presets become free functions returning a full value: `IpmOptions ipm_preset(std::string_view)`
  (the existing table) and `SqpOptions sqp_preset(std::string_view)` ("default" only until M8's labeled
  configs).

### 3.2 The solve family and the result
- On both: `XResult solve(ClaimStreamSource &model, const Vec &x0, SolveBudget budget = {})` and
  `XResult solve(ClaimStreamSource &model, const Vec &x0, const WarmStartData &warm, SolveBudget
  budget = {})`. The model is borrowed for the call. `SolveBudget` carries the SQP's probe budget
  (`minor_budget`) and an iteration cap both engines honour; the IPM's per-phase `max_iters` stays in
  its options.
- The IPM's five phase-named entries (`optimize`, `solve`, `solve_optimize`, `optimize_solve`,
  `solve_optimize_solve`) become `IpmOptions::phases` — a sequence of `IpmPhase` (`kOptimize`,
  `kSolve`), default `{kOptimize}`. The `result()` accessor, `set_nlp`/`release`, the `shared_ptr`
  binding and the model-taking constructor go.
- `SolveStatus` in `hven::solvers`: `kOptimal`, `kAcceptable`, `kMaxIter`, `kInfeasible`,
  `kDiverging`, `kNumericalError`, `kBudgetExhausted`, `kInterrupted`. Each engine's header documents
  which values it can reach (the IPM reaches all but `kInfeasible`/`kBudgetExhausted` today; the SQP all
  but `kAcceptable`/`kDiverging`). `const char *to_string(SolveStatus)` and `int severity(SolveStatus)`
  (the IPM's `operator<=>` ordering, made a function). `hven::ConvergenceFlags` and
  `hven::solvers::SqpStatus` go. Mapping: CONVERGED→kOptimal, ACCEPTABLE→kAcceptable,
  NOTCONVERGED→kMaxIter, DIVERGING→kDiverging, SINGULAR_KKT→kNumericalError.
- `SolveResult` — the core, declared space on both: `status`, `x`, `lambda_e`, `lambda_i`, `z` (bound
  duals), `f`, `stationarity`, `feasibility` (inf-norm over both constraint classes), `ce`, `ci` (the
  residual vectors both engines compute), `complementarity`, `iterations`, `wall_seconds`, and
  `WarmStartData export_warm_start() const`. Residual names are the SQP's — they name what they
  measure; the IPM's `kkt_inf_` is `stationarity`, and the SQP's `kkt_residual = max(stationarity,
  feasibility)` is dropped as a field (it is derivable and its name collided).
- `IpmResult : SolveResult` adds what only the IPM has: the phase reports with their timings, the
  fixed-variable treatment the call ran under, the evaluation error log, the factorization counters,
  analysis count and pattern state (today's `kkt_factor_counters()`, `kkt_analysis_count()`,
  `kkt_pattern_is_analyzed()`, `eval_error_log()` — the class loses these accessors), the recovery
  counters (`soc_steps_taken`, `watchdog_activations`, the depth histogram, the `last_*` family).
  `SqpResult : SolveResult` adds `history`, `counters`, `scaling`, `infeasibility_certified`. Counters
  stay per-engine structs in `core/solver_counters.h`, both named `counters` — unifying the counter
  trees is not this task.

### 3.3 Warm start — one protocol
- Argument form only. `stage_warm_start`, `clear_staged_warm_start`, `set_initial_multipliers` and
  `clear_initial_multipliers` go on both. A multipliers-only seed is a `WarmStartData` with an empty
  `primal_`; `x0` is then the start and the engine's seeded-multiplier clamps apply (the IPM's
  `kSeededIqMultFloor`/`kSeededMultInitMax`, the SQP's `kSeededDualClampTol` — one shared pair of
  constants in `warmstart/` from this commit).
- Same checks at the same points on both: finiteness and payload self-consistency when the payload is
  handed over; block lengths and the structure stamp against the model's declaration key at solve entry.
- **Stamp mismatch REFUSES on both** (`std::invalid_argument`) — the IPM's rule. The SQP's silent
  degrade of a foreign `WarmStart` argument goes. Its `StartLevel` ladder keeps deciding how much of a
  MATCHING start it uses, capped by `common.start_level`. This is one of group 2's three behaviour
  changes and gets its own pin.
- The SQP's engine-native `WarmStart` (a `detail/` type) leaves the public signature;
  `to_sqp_warm_start` becomes internal; crossover goes through `WarmStartData` only. Continuation and
  mesh transfer (both `detail/warmstart/`) keep their engine-native type internally. The IPM polish
  extension (`hven.ipm.polish.v1`) stays as the one extension.

### 3.4 One iteration callback
- On both: `set_iteration_callback(IterationCallback)` / `clear_iteration_callback()`, `IterationCallback
  = std::function<CallbackAction(const IterationEvent &)>`, `CallbackAction { kContinue, kStop }`.
  `IterationEvent` is one view for both engines: iteration index, objective, the three residuals, the
  step norm, the radius or barrier parameter where the engine has one (absent otherwise — absent is
  `std::optional`, never zero), read-only declared-space `x`, `lambda_e`, `lambda_i`, `z`, elapsed
  seconds. Fired after each accepted major (SQP) / iterate (IPM). `kStop` ends the solve with
  `kInterrupted` (behaviour change two; pinned).
- The SQP gains this hook; the IPM's late callback becomes it (the late callback's `IterateInfo` detail
  type leaves the public surface).
- The IPM's early hook with live KKT-matrix access stays as a labelled IPM-only extension:
  `set_kkt_hook(KktHook)` / `clear_kkt_hook()`, semantics unchanged from W5 T2 (read-only vectors,
  value-mutable KKT, structural mutation refused). Nothing equivalent is invented for the SQP.

### 3.5 Instrumentation and threading
- `attach_trace(TraceSink *)` already matches. `attach_ledger(Ledger *, std::string label_prefix)` comes
  to the IPM with an `IpmSolveRecord` and `Ledger::ipm_records()` / `ipm_summary_table()` beside the SQP's.
- Console printing leaves the IPM loop: a built-in `ConsoleTraceSink` renders both engines' iteration
  events, attached by the solver when `common.print_level > 0`. The IPM's table format is preserved
  LINE FOR LINE (a byte-pin of the printed table on a fixed cell is the proof); the SQP's
  `format_iteration_table` becomes that sink's SQP table. `print_header()` and the fmt calls in the
  IPM loop go; the IPM's `wide_console_` becomes a sink option.
- `common.threads` and `common.reproducible_threads` on both. The SQP gains a thread count applied to its
  QP backend (behaviour change three; default = today's effective value so no pin moves; pinned by a
  counter check at threads=1). Each engine keeps its current default (the IPM's `HVEN_DEFAULT_QP_THREADS`).

**Proof for group 2.** Three named behaviour changes (3.3 refuse, 3.4 interrupt, 3.5 SQP threads), each
with a pin. Everything else: replay 0/75, per-symbol identity where the code did not move (the routing
and QP kernels must be byte-identical — P-SYM with named exceptions for the surface functions), the HS
pins, both suites, the console-table byte-pin, install smoke and export contract after every commit that
touches a public header.

## 7. Open questions for the astra review

1. Whether `IpmKktWorkspace` should be constructed per solve (cheap, keyed reuse inside) or owned by
   `IpmSolver` across solves — the design says owned, keyed on structure epoch + declaration key.
2. Whether `SolveResult` should be a base struct (aggregate inheritance, as written) or a member
   `core` of each engine result — the design prefers inheritance so generic consumer code reads
   `r.status`, not `r.core.status`.
3. Whether `kInterrupted` should instead be reported as `kMaxIter` with a flag — the design says a
   distinct status is the honest one.
