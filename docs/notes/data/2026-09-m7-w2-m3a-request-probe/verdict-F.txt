1. THE SETTLER'S OWN DECLARED ERROR IN THE RULE'S DESIGN.

   The 0.5 bar was set on a denominator that cannot reach it. Checked
   against the headers rather than assumed:

   * `minor_iters` increments ONCE PER PASS of the walk loop --
     `++counters.minor_iters` is the first statement inside
     `for (Index iter = 0; ...; ++iter)` in src/qp/qp_engine.cpp:613, and
     detail/qp/qp_engine.h's COUNTER SEMANTICS note fixes it as a relied-on
     contract. A DROP iteration is a pass and counts.
   * `degenerate_steps` counts 'minor iterations that ADDED A BLOCKING
     CONSTRAINT while moving the iterate by no more than the loop's own
     step tolerance' (solver_counters.h). A pass that only DROPS adds
     nothing and is therefore never a degenerate step, however stuck the
     iterate is.
   * `degenerate_run_max` is 'the longest consecutive run of degenerate
     steps... A run is broken by a minor on which the iterate MOVED, and by
     nothing else: ... a drop iteration and a zero-multiplier probe do not'
     break it (solver_counters.h). So the RUN counter spans the drops the
     RATIO's denominator charges for.

   CONSEQUENCE: in a pure add/drop alternation at a stuck iterate, half the
   passes are drops, so degenerate_steps / minor_iters cannot exceed about
   0.5 BY CONSTRUCTION. The bar was set at the ceiling. That is a defect in
   the rule, declared here by the settler; it is NOT a reason to move the
   bar after the fact, and the MIXED verdicts above stand.

4. WHAT WOULD CONFIRM CYCLING PROPER, AND WHAT IS NOT REACHABLE TODAY.

   Cycling proper is THE SAME WORKING SET REVISITED. Nothing above
   establishes that: `distinct_bound_added` counts distinct VARIABLES ever
   admitted, so a multiplicity of k says each touched variable came back
   about k times, which is equally consistent with a long degenerate CRAWL
   over a combinatorially large family of sets drawn from the same few
   variables.

   The distinguishing observation is a per-minor identity of the working
   SET -- a hash or a signature per pass, and a repeat detector over it.
   NOT REACHABLE FROM ANY PUBLIC SURFACE TODAY, checked rather than assumed:
   QpEngine has NO trace sink at all (no attach_trace, no emit site in
   src/qp/qp_engine.cpp), and its ONLY instrument is the per-SOLVE Ledger
   record this addendum read. The finest public QP granularity is the
   subproblem, never the minor.
