M6 W6 T3 -- INSTALL SMOKE UNDER LTO: A PRE-DECLARED FINDING, NOT A GATE
========================================================================
Plan docs/notes/2026-09-m6-w6-plan.md section 0 J.3 / A2 declared this a FINDING
before it was run, on the premise that "an LTO libhven.a is bitcode; a non-LTO
find_package consumer may not link it -- try the consumer both ways, register the
remedy".  THE PREMISE IS CORRECT AND ONE ARM FAILS.  Nothing here gates T3, and
no library change was made in response: the remedy is REGISTERED below.

HOW THE ARMS WERE BUILT
  scripts/check_install_smoke.sh forwards every extra argument to BOTH configures
  -- hven's own and the smoke consumer's (its header, :44-53) -- so an arm's
  extra -D list is what BOTH sides were configured with.  The workdir was pinned
  under .scratch/w6t3/smoke/<arm>/ via HVEN_INSTALL_SMOKE_WORKDIR rather than the
  script's mktemp -d /tmp default, so the trees survive for the export-contract
  check and for this record.

  The script deliberately pins NO compiler (its header, :22-32): the installed
  consumer is read by the SYSTEM DEFAULT front end.  On this box that is
  GCC 16.2.1, not the clang 22.1.8 the project's presets select -- so the CI
  shape of this check does not exercise clang's LTO at all.  Both were therefore
  run: two arms at the default front end (the shape CI runs), and two with
  -DCMAKE_CXX_COMPILER=/usr/bin/clang++ forwarded to both configures (the shape
  the rest of this task's exercise is in).  "Consumer IPO on/off" is the second
  axis the brief asked for, spelled -DCMAKE_INTERPROCEDURAL_OPTIMIZATION=ON.

WHY, AND WHY GCC DIFFERS
  Under clang thin-LTO the members of libhven.a are LLVM IR bitcode, not ELF
  objects -- reach.txt reads them as "LLVM IR bitcode" against the LTO-OFF arm's
  "ELF 64-bit LSB relocatable".  The consumer's link in the failing arm carries no
  -flto, so clang++ drives the default /usr/bin/ld.bfd with no LLVM plugin loaded,
  and BFD ld cannot read a bitcode member at all.  Adding the consumer's own IPO
  (arm clang-ipo-on) puts -flto=thin on the link line, clang then arranges an
  LTO-capable link, and it succeeds.
  GCC's arms both pass because GCC's LTO objects are ELF files carrying extra
  .gnu.lto_* sections: BFD ld reads them as ordinary objects and its linker plugin
  picks the LTO path up transparently.  Arm gcc-ipo-off's own log shows that
  happening at the CONSUMER's link without the consumer asking for it --
  "lto-wrapper: warning: using serial compilation of 23 LTRANS jobs".
  So the failure is specific to CLANG-BUILT LTO archives consumed without LTO; it
  is not a general property of "IPO on".

THE REMEDY, REGISTERED AND NOT BUILT HERE
  [SUPERSEDED 2026-09-14, W6 T3 fix round 1 -- see CORRECTIONS at the end of
  this file, which narrows the observed failure, corrects what the export
  contract actually forbids, and states four options with their costs.]
  This is not a one-line patch, because the obvious fix collides with a rule the
  tree asserts. An LTO build would have to export a usage requirement -- an
  INTERFACE_COMPILE_OPTIONS / INTERFACE_LINK_OPTIONS carrying -flto -- so a
  consumer's link inherits it. But scripts/check_export_contract.sh:21-24 asserts
  that hven exports NO INTERFACE_COMPILE_OPTIONS AT ALL, deliberately (the root
  CMakeLists.txt's "Codegen flags ... are NOT re-exported here" comment), and CI
  runs that assertion on all three lanes. The candidates, for the settler:
    (1) DOCUMENT THE CONSTRAINT and change nothing: an LTO-built hven install is
        consumable only by an LTO-capable link, and HVEN_LINK_TIME_OPT is OFF by
        default and measured to buy this library nothing. Cheapest; leaves a
        sharp edge for anyone who turns it on and installs.
    (2) EXPORT A CONDITIONAL USAGE REQUIREMENT only when the library was built
        with IPO, and widen the export-contract assertion to admit exactly that
        one case. Correct, but it reopens a contract three CI lanes assert.
    (3) REFUSE THE COMBINATION at configure time: make an install of an
        IPO-enabled hven either an error or a loud warning. Fails fast instead of
        failing at a stranger's link.
  Nothing about the default posture changes under any of them: HVEN_LINK_TIME_OPT
  is OFF, and the CI install smoke (GCC front end) passes either way.
