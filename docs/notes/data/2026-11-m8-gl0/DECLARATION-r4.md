## Findings and the planned fixes (each verified against the code before the fix is written)
1. `mj.row.switching_ratio` divides `pred_df` by `kFunnelDelta * h_old^2` unguarded; at `h_old == 0` that division raises FE_DIVBYZERO (pred_df != 0) or FE_INVALID (pred_df == 0), which dirties the FP flags and traps under FP exceptions, against the measure-only claim. Fix: a free function `detail::switching_ratio_value(pred_df, denominator)` (include/hven/detail/sqp/sqp_major_row.h) that does no division at a zero denominator: +/-inf by the sign of `pred_df` when it is nonzero, quiet NaN when it is zero (or NaN); a nonzero denominator divides exactly as before. The trace output ("inf"/"-inf"/"nan") is unchanged.
2. The non-finite rollback sets `rejections_at_iterate = rollback.rejections_at_iterate + 1` but is not a counted rejection (`rejected_steps` and the histogram do not move), so a later counted rejection lands in bucket 1 with bucket 0 empty. `rejections_at_iterate` feeds the strategy (`StepContext`), so its meaning is not touched (the replay would move). Fix: a second run counter, `counted_run_at_iterate`, advanced only where `rejected_steps` advances, reset wherever `rejections_at_iterate` resets, snapshotted into and restored from the rollback record; the histogram reads it. Invariant added to the existing identity checker: `bucket[k] <= bucket[k-1]` below the saturating last bucket ("5 or more" holds every position from 5 up, so a run of six puts two rejections in it and it is outside the monotone chain).
3. `last_reject_cause()` was declared before `reset()` in `GlobalizationStrategy`, shifting the vtable slots of `reset` and `resume_from_restoration`. Fix: it is moved to the end of the virtual list. docs/migration-0.2.md GL-0 gains the line that custom strategies and the enlarged aggregates require a full rebuild, no mixed objects.
4. The `SqpIterationRow::switching_ratio` comment said "nullopt when no solved subproblem was shown to the strategy". The contract is: present only when the row's QP status is kOptimal, so a judged `qp_failure_step` row is null. The comment is corrected; docs/trace-schema-v1.md already said `kOptimal` and gains the explicit qp_failure_step clause (trace-schema-v0.md does not mention the field).
