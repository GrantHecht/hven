## Declared object map (before the code exists)
Source paths do not change; only the CMake target (and so the object path) does. gates/RS-6a/declared-object-map.txt lists every old -> new object path (88 lines: the objects whose path changes; objects whose path is identical need no line), derived by tools/rs6a_membership.py from the base CMake lists.
The one non-test source in a test executable, bench/ipm_corpus_leg.cpp, is mapped hven_sqp_tests -> hven_bench_tests. The gate generates the same map from the two captured manifests and asserts it EQUALS the declared one (tools/rs6a_objmap_check.py).
Unity class: the four unity objects of hven_interior_tests (tests/interior/.../Unity/) cannot be paired one-to-one with the new unity objects (their 29 sources now live in ipm, model, kkt, core; batches re-compose), so they are removed from both snapshots before the P-SYM compare and compared by tools/psym_union.py:
per-symbol (demangled name) multiset of instruction-body hashes over the whole class, before vs after, static-initialiser symbols (`_GLOBAL__sub_I_*`, `__cxx_global_var_init*`) compared by count of the globals they initialise. Section-relative relocation addends are normalised; named-symbol relocations are kept. This is the declared substitute for the design's "through the object map", which cannot exist for a re-composed batch.
Seam and alloc executables' objects are outside the P-SYM groups (as they always were); library objects recompiled by seams are not compared.
