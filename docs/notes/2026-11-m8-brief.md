## 0. Standing constraints

- **Scope.** M8 is: the API revisit (first, owner); the small-dense measurement round (owner);
  tuning and labelled configs; the published comparison; the trace upgrade; user-facing
  documentation; and the M7 carry, triaged in §5. The roadmap's "first-order mode:
  implementation" (`:254-258`) and its HARD GATE (`:294-295`) are superseded by the 2026-08-31
  amendment. **The first-order mode stays M9.** M8 keeps the amendment's two duties: the
  accuracy-matching rule is defined once here (CP-1), and M8's comparison set is chosen so that
  M9b's like-for-like set is a subset of it.
- **Measure before build.** Every conditional build in this brief has a decision rule. The rule
  is committed before the first row it reads. It is applied mechanically by a committed script.
  Its outcome is recorded whether it fires or not. The M7 form is the template (A4-0 before its
  rows; RETAKE21's rule frozen in its declaration, close §4.2).
- **TRAIN/HOLDOUT.** Every default, threshold, label and selection rule is chosen on TRAIN. The
  HOLDOUT (HS 6, CUTEst 12; hven-bench `docs/sets.md`) is touched only by a declared,
  owner-approved final read (CP-2), run once, after the freeze (TU-4). Any set grown in M8 is
  pinned and split **before** any M8 measurement reads it (EX-2). A problem therefore never
  enters TRAIN after its rows have been seen.
- **Measurement (CLAUDE.md §7, `docs/measurement.md`).** Counters and instruction counts are
  asserted; wall-clock is informational. A quoted timing is serial: one solve, alone,
  `MKL_NUM_THREADS=1`. Co-runs assert deterministic columns only, under a declared protocol.
  Every artifact carries the stamp. A wall-clock-dependent status (a census `dnf_budget` at a
  deadline) is not scheduling-invariant and is never the asserted evidence for a counter claim.
- **Census for walk-touching changes (CEN-R3, adopted here as a rule).** A change that can move the
  SQP walk runs the 57-cell census against the new baseline
  (`bench/baselines/2026-10-m7-close-corpus/`) before it lands, in addition to the 27-cell replay.
  One census may cover a batch of such changes landed together (census cost policy,
  `docs/measurement.md` §5). This closes the M7 gap where 20 f7 path-window movers were gated only
  on a replay that holds no path-window cell (close §2, C180).
- **Licences and firewalls.** SNOPT figures come only from committed harness rows. No SNOPT
  source is read, ever. No GPL dependency. LGPL only with a written case (SIFDecode stays an
  external process, never vendored). Papers on GPL/LGPL solvers are algorithmic references only.
  Knitro enters only as published tables.
- **Platforms.** An Apple/Accelerate value not observed on real Mac hardware is **UNOBSERVED**, as
  is any value the pushed macOS CI lane did not produce. This includes any dense-arm figure on
  Accelerate (`hven/detail/linear/lapacke_shim.h` is the Apple route). Windows evidence is the CI
  lane only.
- **Derived files.** Any dense arm lives in a new Apache-2.0 file. It is never placed inside
  the MPL-derived session files (`pardiso_session.*`, `accelerate_session.*`; CLAUDE.md §6). A
  change to the Pardiso `iparm` surface carries the `IPARM-SURFACE` label and its validation
  evidence. No M8 task is expected to need one.
- **Tycho.** Tycho absorbs the API break on resume. Nothing waits on tycho.
- **Process.** Branch `m8` off `fc5c0349`. Each task is run by a fresh implementer under the box
  protocol, gets an independent review and at most one merged fix round, and closes with the
  settler's read and a ledger line in `docs/notes/2026-11-m8-ledger.md`. `m8` is pushed after
  every landing. Landed commits are never rewritten. `docs/notes/data/**` is frozen except for a

The order follows from these dependencies:

1. **The API settles before anything is built on it.** The options reference is generated from
   the settings surface. Labelled configs name option fields. The trace's human surface names
   statuses and modes. So AP-2 lands before AP-4, TR-1, TU-3 and DC-1.
2. **EX-1 runs first because it feeds AP-1.** Writing the examples is the review's primary input.
3. **DN-0 runs in parallel with the API work.** It is a measurement against the current code,
   on TRAIN. A dense arm adds a selection field to `SymmetricFactor::Options` and, if DN-3 fires,
   a public option. Those names go through AP-1, and the code lands after AP-2, so the break
   window is not reopened.
4. **PF-1/PF-2 run in parallel and land outside the break window.** They change SQP walk
   internals, and AP-2 renames across the same headers. Interleaving the two would make neither
   proof clean. Tuning reads the walk as fixed, so PF lands before TU-1.
5. **The tuning objective needs the H6 summaries.** HB-1's shifted geometric means and profiles
   are both the tuning objective's currency and the comparison's. HB-1 therefore lands before
   TU-1.
6. **The trace comes before tuning.** The roadmap specifies it "early in M8 so tuning runs read
   well" (`:283`). After AP-2 it is the first consumer of the new surface.
7. **The comparison runs once, on frozen code.** The order is TU-4 freeze, then the owner-approved
   holdout read, then the comparison. Nothing tunes after the holdout has been seen.
8. **Documentation comes last.** It describes the approved, tuned surface. Its getting-started
   path is the AP-3 examples.

**Scope valve,** cut in this order if M8 runs long. (1) DN-2/DN-3: the dense KKT assembly and
auto-selection stay registered even if their rules fire. (2) HB-5, the sequenced-workload lane:
the cold-solve comparison ships alone, with the sequenced claim as a named gap. (3) TU-3: no labels
ship, and the selection guidance stays the M7 close §3 form. The API break, the comparison artifact
and the presentation deliverables are never cut.

### EX: the openers

- **EX-1: `examples/` against the CURRENT API, with a friction log.** Each example is one
  self-contained program for one problem. It consumes hven the way a stranger does, through
  `find_package(hven)` against an install tree (the `scripts/check_install_smoke.sh` pattern),
  not `add_subdirectory`. Proposed set, which the owner may amend (§4 Q5):
  1. HS071 on both engines;
  2. an unconstrained/bound-constrained problem (Rosenbrock with bounds);
  3. an equality-constrained problem;
  4. a sparse, partitioned problem in tycho's shape (an assembled declaration with several
     pieces);
  5. warm-started continuation, a parameter swept over a short chain;
  6. the explicit IPM to SQP polish composition (export, then stage);
  7. SQP in quasi-Newton mode (`hessian_mode`);
  8. reading results and diagnostics, attaching a trace sink, and dumping options.

  The friction log is a committed page (`docs/notes/2026-11-m8-ex1-friction.md`). Each entry
  records the example, what was attempted, what was needed (header, type, workaround), and a
  severity. Entries are logged as found, not curated afterward. Friction already on the record
  is pre-seeded, with citations:
  - **Two model contracts.** The IPM takes `NonLinearProgram &`
    (`include/hven/drivers/ipm_solver.h:404`). The SQP takes `const NlpModel &` or
    `NlpModelAssembly &` (`include/hven/drivers/sqp_solver.h:738-1216`). A problem stated as an
    `NlpModel` cannot reach the IPM through any public header, so the harness had to write the
    bridge itself (hven-bench `docs/sets.md`, "Both routes, one definition"). This is the M6 W5
    T8 design's §6 group: "both engines consume the M4 claim stream". It was deferred by the
    owner to "its own M7 task" (`docs/notes/2026-09-m6-w5-t8-design.md:27`, `:465-490`). **The
    M7 brief never scheduled it and neither ledger records it. This brief re-registers it in
    AP-1.**
  - **Three spellings of one iteration cap:** `IpmOptions::max_iters`
    (`ipm_solver_types.h:113`, per phase), `SqpOptions::max_iter` (`sqp_solver_types.h:462`) and
    `SolveBudget::max_iterations` (`solve_result.h:78`).
  - **No whole-solve factorization ceiling** (hven-bench H1 finding F3).
  - **Absent bounds.** Two of two external model sources spell an absent bound as a finite
    `±1e20`, which hven reads as a real bound (hven-bench F9/F10, "registered for the owner, not
    acted on").
  - **Public headers include `detail/` headers:** `sqp_solver.h` has 14 such includes,
    `ipm_solver.h` 7 and `non_linear_program.h` 7.
  - **Test-internal names in a public header:** gtest friend declarations at
    `include/hven/solver_interface_adapter.h:50-53`.
  - **No umbrella header.** The public namespace is `hven::solvers` (96 opens), while CLAUDE.md
    §1 states `hven::`.
  - **Asymmetric construction:** `IpmSolver(IpmOptions = {})` but `SqpSolver(const SqpOptions &)`
    with no default.
- **EX-2: set growth and split, before any M8 measurement.**

### DN: small dense problems (owner direction 1)

Verified starting point. `hven::linear::DenseSymmetricFactor`
(`include/hven/linear/dense_symmetric_factor.h:78`) is LAPACK `dsytrf`/`dsytrs` with
`BunchKaufmanBlockEvidence` (absent-never-zero through `block_evidence()`). Its only library
consumer is the Schur-complement border stack (`include/hven/detail/kkt/schur_complement.h:651`).
`SymmetricFactor` (`include/hven/linear/symmetric_factor.h:241`) is a concrete class with no
virtual member. Its backend is chosen at build time: one `detail::FactorSession` per platform
(`pardiso_session.h:201`, `accelerate_session.h:128`), with `symmetric_factor_mkl.cpp` and
`symmetric_factor_accelerate.cpp` as alternatives. The engines hold it by value through two
wrappers, `KktFactor` (SQP; `detail/kkt/kkt_calls.h:54`) and `KktFactorization` (IPM;
`detail/interior/kkt_factorization.h:29`), plus direct uses in `src/drivers/equality_basis.cpp`
and `src/qp/ws_independence.cpp`. **No runtime dispatch seam exists.** A dense arm needs one,
inside `SymmetricFactor` or at those four consumers. The factor's contract has precedent for a
capability that varies by backend (`supports_partial_solve()`, false on Accelerate).

- **DN-0: the measurement round.** TRAIN only: HS TRAIN (22) plus EX-2's small-dense CUTEst TRAIN,
  both engines, at the shipped defaults. It runs serial under `docs/measurement.md` §4's
  instruction-count protocol (`perf stat` / `perf record`, `instructions:u`), and wall-clock is
  informational. Per cell, instructions are attributed to six buckets: **B_sym** (symbolic
  analysis), **B_fac** (numeric factorization and solves, hven::linear plus backend symbols),
  **B_kkt** (KKT assembly, scatter, layout), **B_eval** (model evaluation including any bridge),
  **B_setup** (one-time solver and model construction other than B_sym), and **B_eng** (the
  rest). A dense replay runs alongside. Every KKT matrix a cell factorizes (or the first 50, if
  more) is dumped, then factored and solved both ways in isolation:
  - `SymmetricFactor`, analyze plus factorize plus solve;
  - `DenseSymmetricFactor::try_factorize` plus `solve`, on the densified matrix.

  Both are measured in instructions, and the replay records negative-eigenvalue agreement against
  the sparse `InertiaEvidence`. Deliverable: a page and CSV with the bucket table per cell and the
  replay ratio `rho = dense / sparse` per cell.

  **The pre-registered rule** is committed with the DN-0 declaration before its first leg. It is
  read per engine on the population's median cell (by total instructions), and separately on each
  population.

  | fires | condition | then |
  |---|---|---|
  | **DN-1** (dense arm behind the factor layer) | `(B_sym + B_fac) / total >= 0.40` **and** `rho <= 0.5` on that cell, **and** negative-eigenvalue counts agree on >= 99 % of replayed matrices | build DN-1 |
  | **DN-2** (dense KKT assembly) | `B_kkt / total >= 0.25`, measured after DN-1 if DN-1 was built | build DN-2 |
  | **no dense build** | neither fires | record which bucket dominates. If it is B_setup or B_eval, that bucket is registered as the small-problem lever with its numbers, and no dense code is written in M8 |

  The DN-1 threshold is a projected saving of at least 20 % of a median solve's instructions. A
  smaller saving does not repay a second backend's test and contract surface.
- **DN-1 (conditional): the dense arm.**
  - **Design page first.** It places the seam: inside `SymmetricFactor` (a runtime arm beside
    the platform session), or a two-way choice at the four consumers. It states how the dense
    arm honours each part of the factor contract:
    - the `(pattern_hash, session_id, epoch)` identity triple;
    - `share()`/`adopt()`;
    - `InertiaEvidence`, where fields the dense path cannot produce (for example
      `perturbed_pivots`; Bunch-Kaufman does not perturb) are ABSENT, never zero;
    - `Counters`;
    - `solve_partial`, either supported or refused by capability.
  - **The sparse path is proven untouched** (CLAUDE.md §5): a compile-flags diff, the 27-cell
    replay and census byte-identical with the arm compiled in and not selected, and instruction
    counts within the ±0.5 % corpus bar.
  - **Proof for the dense arm:** on DN-0's population with the arm forced, every cell keeps its
    status and objective to 1e-8 relative. Iteration counts may move, declared per cell. Measured
    instruction savings are reported against the DN-0 projection.
  - **Selection:** an explicit option, default OFF until DN-3.
- **DN-2 (conditional): dense KKT assembly.** The engine assembles straight into column-major
  storage for the dense arm and skips CSR. It has the same proof form as DN-1.
- **DN-3 (conditional on DN-1): measured auto-selection.** A size/density threshold
  `(n_kkt, nnz / n_kkt^2)` is chosen on TRAIN by a rule pre-registered at DN-1's close:
  - the threshold is set where the replay ratio crosses 1, from the replay corpus;
  - auto-selection is adopted as the default only if, on HS TRAIN plus small-dense TRAIN, it wins
    on at least one family and loses on none (the RETAKE21 per-cell rule, counter =
    instructions);
  - every cell above the threshold stays byte-identical, so the 27-cell replay and census do not
    move.
- **Not in M8:** dense updates inside the QP engines (the walk's Schur updates, IPQP). These are
  a larger, separate item, registered beyond M8 with DN-0's numbers as its motivation, if they
  support it.

### TU: tuning and labelled configs (TRAIN only)

- **TU-1: pilot and rule.** The question is structured manual sweeps against automated
  configuration in the SMAC/irace tradition (papers only), on a pre-registered pilot rule.
  Automated configuration is adopted only if, under 3-fold cross-validation inside TRAIN, its best
  configuration beats the best manual sweep by the TU-2 adoption rule on held-out folds. **The
  TU-2 adoption rule is frozen at TU-1.** It is the RETAKE21 rule (close §4.2): per cell, a win is
  converged where the baseline did not, or both converged and the primary counter is at least
  10 % lower. A family's sign is net wins. A default moves only if it wins on at least one family
  and loses on none. The primary counter is factorizations for the SQP and iterations for the IPM.
  There is one more veto: the 57-cell census may not lose a status that is not deadline-dependent.
  TRAIN is small (HS 22, CUTEst 23), so the families are fixed at TU-1 and never re-cut after
  rows are seen.
- **TU-2: tuning.** The candidate pool is §5 group 1, plus the earlier registers that are levers
  (A1-R4..R6, A2-F1..F4/R1..R3, A3-R2..R5, A7-R1..R4, W3-R1..R5, SCL-R2), plus whatever TU-1's
  pilot surfaces. Each adopted default is a declared default event, with its census and replay.
  **Precondition:** if a candidate moves an IPQP barrier default, M7-42's certification fixture
  class (built from `Sigma = 2 mu_stop / s^2`) is built first. If none does, M7-42 retires at the
  close.
- **TU-3: labelled configs.** These are curated settings of existing fields, never a separate
  mechanism (roadmap settings contract). A label ships only if a cluster is defined before rows
  are read, from CUTE classification codes and problem dimensions. The cluster must have at least
  five TRAIN cells, and a configuration must win against the tuned default on that cluster by the
  TU-2 rule while losing on no other family. If no cluster separates, no label ships, and that is
  a result.
- **TU-4: the freeze.** A declaration fixes the code pin, the defaults, the labels and the
  comparison's lane options. Nothing after it tunes.

## 4. Open to the owner

**Q1. API break: scope and deprecation policy.**
*Recommendation:* one declared break, with no deprecation shims. hven is at 0.1.0
(`CMakeLists.txt:2`) with one consumer that absorbs breaks on resume. Shims would double the
surface the review exists to shrink, and they would keep the confusion visible in the examples.
The migration guide carries every rewrite. The version moves to 0.2.0 at the break. The
model-contract unification (T8 §6) is **in scope**. It is the root of the two-entries friction,
and it was already deferred once and then dropped by omission. If AP-1's eight-coupling
specification sizes it beyond about a third of the milestone, it splits into its own group,
landing after the rest of the break and before TR-1. From M8's close on, a policy for future
breaks: one window per milestone at most, always with a guide.

**Q2. Which published tables to compare against.**
*Recommendation:* Mittelmann's current NLP benchmark pages as the single Knitro source, retrieved
and transcribed under HB-4, with Knitro claims made only on the problem overlap with our pinned
sets and only relative to the IPOPT anchor. If the overlap is fewer than 10 problems, the Knitro
row is reported as "insufficient overlap" and no Knitro claim is made. The comparison's weight
then rests on the local SNOPT and IPOPT lanes over the full pinned sets. The AMPL-NLP set stays
deferred (`.mod` only, no AMPL on the box). Adding CUTEst instances to raise the overlap is
allowed only through EX-2, before tuning. Decide whether to accept the 10-problem floor.

check on overfitting, not a standing claim of its own. After this read it is spent for these
defaults: M9b's tuning needs a fresh HOLDOUT, from a new set version split before it is seen.
